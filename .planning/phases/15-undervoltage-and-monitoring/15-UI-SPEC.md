# Phase 15 — UI Design Contract

> Visual and interaction contract for the dashboard additions in Phase 15. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This phase touches exactly three surfaces in `src/shitbox/dashboard/static/index.html`:

1. The transient full-screen alert overlay (colour-branch it for recovery vs failure).
2. The existing Hardware modal — rename in copy to **Health**, extend with a new "System" section above the hardware list for sticky system-condition rows.
3. The SSE `/sse/slow` payload shape — add `system_conditions[]` sibling to `hardware[]`.

No new routes, no new views, no build step. Everything extends existing tokens already live in the kiosk dashboard.

## System Condition Row — Layout Contract

Three rows always present in the new SYSTEM section, in this order (research Open Question 3 recommendation, locked here):

1. **UNDERVOLTAGE**
2. **THERMAL**
3. **CAPTURE**

Each row uses the existing `hw-row hw-row-lg` template (`index.html:29-33, 396-404`) with an adapted state-class prefix:

| State | CSS class suffix | Glyph | State-text colour | Pill fill | Pill text |
|-------|------------------|-------|-------------------|-----------|-----------|
| Never fired / faded idle | `sc-clear` | `○` | `#8b949e` | `#161b22` border `#21262d` | `CLEAR` |
| Active (condition firing) | `sc-active` | `●` | `#f85149` | `#da3633` | `ACTIVE` |
| Mid-recovery (capture only) | `sc-recovering` | `◐` | `#d29922` | `#d29922` | `RECOVERING` |
| Restored (bounded) | `sc-restored` | `●` | `#238636` | `#238636` | `RESTORED` |

Row cadence rules (locked):

- `ACTIVE` state persists until the helper observes recovery. Sticky — this is the whole point.
- `RESTORED` persists for **60 seconds** after the recovery signal, then fades back to `CLEAR`. Matches D-12's "no nagging" TTS cadence and mirrors Phase 21 D-09 "positive confirmation but not permanent celebration". Implemented client-side as a setTimeout on the row; server emits `system_conditions[].state = "restored"` with `since_ms` driving the client-side expiry (client fades when `since_ms > 60000`).
- `RECOVERING` is emitted by the server only between `CAPTURE_FAILURE` fire and either `CAPTURE_RESTORED` or `CAPTURE_DOWN` transition. Undervoltage and thermal skip this state — they are binary.
- Section order within Health modal: SYSTEM section above HARDWARE section. Rendered even when all three are `CLEAR` — the driver should be able to glance and see "all three conditions clear" without reading.

## Alert Overlay — Colour Branch Contract

Extend `showAlert(payload)` at `index.html:536-548` with subtype-aware colour + duration routing. Do not introduce a second overlay element — reuse `alertOverlay` div at `index.html:217-224`.

| Subtype ends in | Overlay colour | Duration | Typography |
|-----------------|----------------|----------|------------|
| `_CLEARED` / `_RESTORED` | `#238636` (green) | 3000 ms | 101px / 700 — unchanged |
| anything else (including `CAPTURE_FAILURE`, `CAPTURE_DOWN`, `UNDERVOLTAGE`, all `THERMAL_*`) | `#da3633` (red) | 10000 ms | 101px / 700 — unchanged |

Implementation note (for the planner): change the `colour` and `duration` ternaries in `showAlert` to branch on `payload.subtype` suffix. The existing event-type branch (non-`ALERT` path) is untouched.

Accessibility non-negotiables:

- Colour is never the sole signal. The overlay always shows the message text ("POWER RESTORED", "UNDERVOLTAGE DETECTED") — a monochrome photo of the screen must still convey which condition fired.
- State pills on the Health page always pair colour with a state word (`ACTIVE`, `RESTORED`, `CLEAR`, `RECOVERING`). No pill-colour-only states.

## SSE Payload Shape — Health Contract

`/sse/slow` gains a `system_conditions` key alongside the existing `hardware` key. Shape mirrors `_hardware_payload()` exactly — five scalar fields, no nested arrays.

```json
{
  "system_conditions": [
    {
      "role": "undervoltage",
      "label": "UNDERVOLTAGE",
      "tier": "critical",
      "state": "active",
      "since_ms": 134000
    },
    {
      "role": "thermal",
      "label": "THERMAL",
      "tier": "critical",
      "state": "clear",
      "since_ms": null
    },
    {
      "role": "capture",
      "label": "CAPTURE",
      "tier": "critical",
      "state": "restored",
      "since_ms": 23000
    }
  ]
}
```

Field rules:

- `role` ∈ `{"undervoltage", "thermal", "capture"}` (lowercase — matches existing hardware roles)
- `label` always UPPERCASE — matches existing hardware row-label weight/casing
- `tier` always `"critical"` for this phase — all three conditions are driver-safety-relevant
- `state` ∈ `{"clear", "active", "recovering", "restored"}` (lowercase — matches hardware state values `present`/`degraded`/`missing`)
- `since_ms` — millis since last transition into current state, or `null` when `clear` has never fired
- No `history`, no `last_message`, no `raw_bitmask`. Log detail lives in structlog, not SSE (RESEARCH Pitfall 5).

## Layout — 7-inch Screen Budget

The Health modal is full-screen (`inset: 0`) so screen budget is not a constraint on the main dashboard grid. The one risk is the modal scroll length on a 1024×600 display:

- Existing: modal has ~460px of usable vertical space for the hardware list (title 80px + banner ~56px + footer ~110px + padding ~20px).
- Added: SYSTEM section header (~30px) + three rows × 70px (`hw-row-lg` height) = ~240px.
- Remaining for hardware list: ~220px. 14 declared devices × ~70px = ~980px — already scrolls. Adding SYSTEM above does not change the scrolling behaviour (container is `overflow-y: auto`), only pushes devices further down the scroll.

Acceptable. SYSTEM section is at the top of the scroll so the three system conditions are immediately visible when the modal opens — matches the "sticky colour principle" intent.

No layout change on the main kiosk view. The existing `HW` button (line 94-99) already flashes red via `hwBadgeClass()`; this phase piggybacks on that behaviour for system conditions.

## Out of Scope for This UI-SPEC

Flagged here so the planner does not accidentally pull them in:

- **Website Health page** — Phase 21 D-10 (status is Pi-local only). No `hardware.json` or `system_conditions.json` sync generator.
- **Button-as-acknowledge** for active conditions — Phase 21 D-05 deferral.
- **Criticality-tier escalation UI** (repeated TTS, OLED-line inversion under active red) — Phase 21.
- **Per-condition detail drawer** (click-through to see full throttle bitmask history or stall stderr) — structlog is the audit trail for this phase.
- **Colour-blind mode / theme switcher** — existing dashboard is dark-only; state + glyph + word pairing covers CVD without a theme switch.
- **Animation** on state transitions — the existing dashboard has no transitions outside the bearing arrow, and adding them here introduces CPU cost the capture path cannot tolerate (Phase 10 D-02). Rows snap between states.
