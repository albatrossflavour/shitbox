# Phase 28: TPMS Integration — User Acceptance Tests

**Status:** pending hardware bring-up (Thursday 2026-04-30 — Nooelec NESDR Smart v5)
**Owner:** Tony
**Pre-reqs:**
  - Plans 28-01 through 28-05 shipped + green pytest suite
  - Pi running latest shitbox daemon (`systemctl status shitbox-telemetry` shows active)
  - `rtl_433 -V` reports 22.11-1 (Pi OS bookworm)
  - All four TPMS sensors fitted to wheels, vehicle stationary on level ground

## UAT-1 — Hardware Bring-Up Sanity (verifies A4, A5)

**Why first:** the apt-installed `rtl_433` and the Nooelec NESDR's actual
USB VID:PID need to be checked against assumptions baked into config.yaml
before any other UAT will work.

**Steps:**

1. Plug the Nooelec NESDR Smart v5 into a direct USB 2.0 port on the Pi
   (not behind a hub — bus contention causes sample drops per the project
   memory).
2. SSH to the Pi: `ssh tgreen@10.10.20.107`.
3. Confirm the chipset enumerates: `lsusb | grep -i realtek`.
   - **Expected:** a line containing `ID 0bda:2838 Realtek Semiconductor
     Corp.`. If it shows `0bda:2832` or another PID, update
     `tpms.usb_vid_pid` in `config/config.yaml` and restart the daemon.
4. Confirm protocol 156 is the Abarth-124 decoder:
   `rtl_433 -R help 2>&1 | grep -i "abarth\|124"`.
   - **Expected:** `[156]  Abarth-124Spider / VDO-TG1C TPMS`. If the
     index has shifted, update `tpms.rtl433_protocol_id` in
     `config/config.yaml`.
5. Confirm USB power flag set:
   `grep usb_max_current_enable /boot/firmware/config.txt`.
   - **Expected:** `usb_max_current_enable=1`. If absent, append it and
     reboot before continuing — the Pi 5 600 mA cap will drop the SDR
     under load otherwise.
6. Restart the daemon: `sudo systemctl restart shitbox-telemetry`.
7. Tail the log for 60 seconds:
   `sudo journalctl -u shitbox-telemetry -f --since "30 seconds ago"`.
   - **Expected:** `tpms_starting`, `tpms_rtl433_started`, then
     `tpms_frame_received` lines for each of the four sensor IDs within
     ~60 seconds.

**Pass criteria:**
- [ ] All four sensor IDs (`550b57d9`, `54d96e8f`, `550d14ed`,
      `550b5d8a`) appear in at least one `tpms_frame_received` log line
      within 2 minutes
- [ ] No `tpms_unknown_sensor` lines (sensor map is correct)
- [ ] No `tpms_rtl433_exited` lines (subprocess stable)

## UAT-2 — Bench Deflation: Low + Leak alerts

**Why:** SPEC-7 (red banner + TTS at ≤25 PSI) and SPEC-8 (≥5 PSI/60s
leak detection) are unverifiable from the bench without actually
deflating a tyre. Use the front-driver wheel (`550b57d9`) as the test
target — closest to the kerb if you're working solo.

**Setup:**
- A stick gauge (digital preferred; the existing analog one is fine if
  it's the only one to hand).
- Phone/laptop with a browser open to the Pi dashboard:
  `http://10.10.20.107:8080/` → Health modal.
- TTS audible: connect the USB speaker, set volume so cabin TTS is
  hearable from outside the car.

**Steps:**

1. Note the starting front-driver PSI from the dashboard (should be
   ~31-32 PSI within ±3 PSI of stick-gauge).
2. **Sustained-low test (SPEC-7 red threshold):**
   a. Slowly bleed the front-driver tyre using the valve core. Aim to
      reach ~26 PSI (yellow band, 25 < PSI ≤ 28) over 30-60 seconds.
   b. **Expected:** the FD row on the dashboard turns yellow with
      "LOW" status. **No TTS.** This is intentional — yellow is a Health
      page colour only.
   c. Continue bleeding until PSI ≤ 25.
   d. **Expected within ~5 seconds (sustain_required=2 frames at ~1 Hz):**
      FD row turns red with "CRITICAL"; TTS speaks "Front driver tyre
      low pressure".
   e. Re-inflate above 28 PSI.
   f. **Expected within ~5 seconds:** TTS speaks "Front driver tyre
      pressure restored"; FD row turns green ("OK").
3. **Leak test (SPEC-8 ≥5 PSI/60s):**
   a. Re-inflate to ~32 PSI.
   b. Open the valve core fully and bleed rapidly so the wheel drops
      ≥5 PSI within 60 seconds (down to ~27 PSI is enough — no need to
      go below 25).
   c. **Expected within ~5 seconds of crossing the 5 PSI delta:** TTS
      speaks "Tyre leaking, front driver"; FD row turns red with
      "CRITICAL"; the most recent event in the events ticker (or
      `events.json` on disk) shows a `tpms_leak` event for FD.
   d. Re-inflate to ~32 PSI; wait 60+ seconds for the deque window to
      clear.
   e. **Expected:** FD row returns to green. No further TTS for the
      leak (Phase 15 sustain semantics — leak is a single-shot fire).
4. **Slow deflation negative test (SPEC-8 false positive guard):**
   a. Re-inflate to ~32 PSI.
   b. Bleed VERY slowly — aim for 1 PSI lost over 60+ seconds (this is
      "tyre cooling overnight" rate, not a leak).
   c. **Expected:** no TTS, no `tpms_leak` event, no red banner. PSI
      drifts down by 1-2 across 2-3 minutes; row stays green/yellow only.

**Pass criteria:**
- [ ] Stored PSI (per `sqlite3 telemetry.db 'SELECT * FROM tpms_readings ORDER BY id DESC LIMIT 4'`) within ±3 PSI of stick-gauge at every checkpoint
- [ ] Yellow state shows on dashboard but no TTS fires for 25 < PSI ≤ 28
- [ ] Red state + TTS fires within 5s of crossing PSI ≤ 25
- [ ] `_RESTORED` TTS fires within 5s of re-inflating above 28 PSI
- [ ] Leak alert fires within 5s of crossing the 5 PSI/60s threshold
- [ ] `events.json` contains a `tpms_leak` event for the front-driver wheel
- [ ] Slow 1 PSI/min deflation does NOT trigger leak alert

## UAT-3 — RTL-SDR Replug Recovery (SPEC-10)

**Why:** SPEC-10 requires graceful degradation — the daemon must keep
running when the SDR vanishes, and re-adopt within the
`HardwareSupervisor` exponential-backoff window when it returns.

**Steps:**

1. Confirm the daemon is running and TPMS frames are flowing
   (`journalctl -u shitbox-telemetry -f` shows `tpms_frame_received`
   regularly).
2. On the dashboard Health modal, confirm the `tpms_radio` row shows
   PRESENT (under HARDWARE section, criticality `best_effort`).
3. Physically unplug the SDR from the Pi.
4. **Expected within ~30 seconds (DEVICE_MISSING_BACKOFF_S=30):**
   - `tpms_rtl433_exited` log line followed by `tpms_sdr_missing`.
   - `tpms_radio` row in the HARDWARE section flips to MISSING (orange
     for best_effort).
   - **Daemon does NOT restart** — `systemctl status shitbox-telemetry`
     still shows the same uptime.
   - TPMS rows in the Health modal go to STALE within 5 minutes (per
     SPEC-9 timeout).
5. Wait 60 seconds, then plug the SDR back in.
6. **Expected within ~30-60 seconds:**
   - `lsusb` shows `0bda:2838` again.
   - `hw_state_changed` log line with `role=tpms_radio, state=present`.
   - `tpms_rtl433_started` followed by `tpms_frame_received` for each
     wheel.
   - Dashboard FD/FP/RD/RP rows return to OK / LOW / CRITICAL state
     based on actual PSI.

**Pass criteria:**
- [ ] Daemon does not exit/restart during unplug
- [ ] `tpms_radio` MISSING surfaces on Health modal within 30 seconds
- [ ] All four TPMS rows go STALE within 5 minutes of unplug
- [ ] Replug results in PRESENT + frames flowing again within 1 minute
- [ ] No journalctl error spam during the missing window (back-off
      working)

## UAT-4 — Driving Loop End-to-End (SPEC Acceptance — final gate)

**Why:** the canonical acceptance check from `28-SPEC.md` Acceptance
Criteria last bullet. RF reception in real driving (engine vibration,
RF interference, varying wheel positions) is meaningfully different
from a stationary bench.

**Steps:**

1. Pre-drive: confirm UAT-1 + UAT-2 passed. Note the starting PSI from
   the stick gauge for all four wheels.
2. Drive a familiar 10-15 minute loop (e.g. local roundabout circuit).
   Vary speed: 20-80 km/h, include at least one stop.
3. While driving, glance at the dashboard (passenger or co-driver
   reads — not the driver) every 2-3 minutes. Confirm all four wheels
   continue to show OK with PSI within ±3 PSI of the pre-drive stick
   gauge.
4. After ~5 minutes of driving, intentionally deflate ONE wheel via the
   valve core during a stop (front-driver again — easiest from inside
   the car if reachable, or step out and bleed). Aim for ~24 PSI
   (below the 25 PSI red threshold).
5. **Expected within ~5 seconds of deflation completing:** TTS speaks
   "Front driver tyre low pressure"; FD dashboard row red.
6. Continue driving for 1-2 more minutes — confirm the alert sticks
   (no flapping back to OK on weaker signal).
7. End of loop: stop, re-inflate FD to ~32 PSI, wait for `_RESTORED`
   TTS.
8. Open Grafana (`http://grafana.homelab.local/d/shitbox-rally-command`):
   confirm `shitbox_tpms_pressure_psi` shows four time series for the
   loop duration, with FD dropping then recovering.

**Pass criteria:**
- [ ] All four wheels report frames continuously through the loop (no
      wheel goes STALE during driving — RF reception is good enough)
- [ ] Stick-gauge to dashboard PSI agreement within ±3 PSI at start
      and end
- [ ] Mid-loop deflation alert + TTS fires within 5 seconds
- [ ] Re-inflation `_RESTORED` TTS fires within 5 seconds
- [ ] Grafana panels show four labelled time series matching SQLite
      content (`sqlite3 telemetry.db 'SELECT wheel, COUNT(*) FROM tpms_readings GROUP BY wheel'`)
