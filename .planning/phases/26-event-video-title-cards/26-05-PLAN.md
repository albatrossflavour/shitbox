<objective>
Close CR-01 from 26-VERIFICATION.md. The existing plan (26-04) wired the storage
and rendering sides correctly, but the poster PNG lives inside the per-save
`tmp_dir` that the ring-buffer worker's `finally` block `shutil.rmtree`s
immediately after firing the save callback. The engine's telemetry-thread
`_check_post_captures` only runs `post_event_seconds` later, by which time the
PNG is gone. `src_png.exists()` silently returns False, `poster_path` stays
None, and events.json never carries `poster_url` in the common case.

**Fix chosen:** option 1 + option 3 combined (Option A — narrow, faithful to
existing behaviour). Move the PNG out of `tmp_dir` to a stable holding dir
(`buffer_dir/pending_slates/<save_id>.png`) on the worker thread BEFORE the
`finally` fires, pass that stable path as a NEW argument to the save callback,
and have the engine's `_on_video_complete` (also invoked on the worker thread)
capture it into a lock-protected `_event_poster_paths` dict keyed by event id —
exactly the same pattern the existing `_event_video_paths` dict already uses
for the MP4 path. The telemetry-thread `_check_post_captures` then pops from
`_event_poster_paths` instead of reaching into
`VideoRingBuffer._pending_slate_png`, renames to
`<day_dir>/<base_name>_poster.png`, and calls `save_event(poster_path=...)`
as today.

Narrow-scope note (Option A, not B): the existing engine callback lambda
`callback=lambda path, _cs, _eid=eid: self._on_video_complete(_eid, path)`
passes `_cs` into the lambda but the callee (`_on_video_complete`) has never
accepted or used `clip_start_mtime` — `_cs` is silently dropped in the lambda
today. This plan preserves that behaviour: the new lambda accepts `_pp` (poster
path) as a FOURTH lambda parameter and forwards `_eid, path, _pp` to
`_on_video_complete`, which becomes a 3-argument method
`(event_id, path, poster_path)`. We do NOT promote `clip_start_mtime` to a
first-class callee parameter — that would be a scope widening (Option B,
rejected). The latent `_cs` drift stays latent; if it ever becomes
load-bearing, a follow-up phase can address it.

Why this combo (not option 2 alone, not option 3 alone):
- **Option 1 alone** (stable dir from the start) leaves orphan files when the
  engine never gets to them. The `pending_slates/` startup sweep fixes that.
- **Option 3 alone** (callback extra arg, no holding dir) would make the PNG a
  pointer into a dir that the `finally` is about to delete — still fragile if
  the callback is reordered later. Relocating first makes the invariant
  explicit: once the callback returns, the path the engine holds is stable.
- **Option 2 alone** (synchronous move in the callback) requires the engine to
  know the event's `base_name` on the worker thread, which forces
  `_generate_filename` (and its counter increment) into the worker callback
  rather than staying co-located with the other `save_event` prep in
  `_check_post_captures`. T-26-04-06 double-bump hazard re-opens.

Secondary: retire `VideoRingBuffer._pending_slate_png` as cross-thread state.
After this plan, only `_pending_slate_ts` and `_pending_slate_duration` remain
on the ring buffer, and both are read/written exclusively on the worker thread
during `_concatenate_segments` — the concurrency concern flagged in WR-02 is
reduced to the PNG handoff being explicit rather than implicit.

Purpose: restore ROADMAP criterion #3 ("`<event>_poster.png` is persisted
alongside the MP4; events.json carries `poster_url` for every event where the
poster exists on disk"). This is the last gap in Phase 26 — all other
criteria verified or passed human verification on re-run.

Output: two modified source files, three modified/new test files. New
integration test exercises the full `save_event → rmtree → _check_post_captures`
sequence that unit tests in 26-04 bypassed. No changes to storage.py,
title_card.py, labels.py, or config.py — the storage-side contract from
26-04 Task 1 is untouched.

Regression constraints (MUST NOT REGRESS from 26-01..26-04):
- `EventStorage.save_event` signature stays exactly as 26-04 established
  (`poster_path: Optional[Path] = None`, `base_name: Optional[str] = None`)
- Concat-demuxer path, PiP setpts offset, ASS head_offset_s math all unchanged
  (ROADMAP criterion #6 is verified)

  `poster_url` (ROADMAP criterion #2 is verified)
- Graceful-degradation matrix (Pillow missing, ffmpeg missing, renderer
  raises) still produces `(None, None, 0.0)` from `_render_slate` and a
  working MP4 downstream
- `_pending_slate_ts` and `_pending_slate_duration` semantics preserved —
  worker-thread-local, read inside `_concatenate_segments` and the offset
  builders, reset per save pass
- `clip_start_mtime` remains dropped in the engine lambda as it is today —
  narrow fix, no scope widening.

```python
# Recommended sweep: delete any file in self._pending_slates_dir older than
# self._process_start_time (set in __init__ or start()). Scheduled on start()
# so a crash-restart doesn't leak prior-run PNGs. Also guard against the
# race where a `save_event` fires an async thread between start() and the
# sweep: only delete files whose save_id-prefix is < current _save_counter
# AND whose mtime is older than _process_start_time (both must hold).
def _cleanup_pending_slates(self) -> None:
    try:
        for entry in self._pending_slates_dir.iterdir():
            if not entry.is_file():
                continue
            mtime_ok = entry.stat().st_mtime < self._process_start_time
            # filename shape: "<save_id>.png"; save_ids monotonically increase.
            try:
                save_id_from_name = int(entry.stem)
                id_ok = save_id_from_name < self._save_counter
            except ValueError:
                id_ok = True  # unrecognised name — treat as orphan
            if mtime_ok and id_ok:
                try:
                    entry.unlink()
                except OSError:
                    pass
    except FileNotFoundError:
        pass
```

    def _cleanup_pending_slates(self) -> None:
        """Sweep pending_slates/ of orphan files from crashed prior runs.

        Mirrors _cleanup_buffer's pattern. Guards against the rare in-run
        race where `save_event` fires a thread before start() completes by
        requiring BOTH mtime < process-start AND save-id-from-filename <
        current _save_counter. (save_event does not itself check is_running
        before spawning, so the sweep cannot assume no writer is racing it.)
        Silent on empty dir.
        """
        try:
            entries = list(self._pending_slates_dir.iterdir())
        except FileNotFoundError:
            return
        removed = 0
        for entry in entries:
            try:
                if not entry.is_file():
                    continue
                mtime_ok = entry.stat().st_mtime < self._process_start_time
                try:
                    save_id_from_name = int(entry.stem)
                    id_ok = save_id_from_name < self._save_counter
                except ValueError:
                    id_ok = True  # unrecognised name — treat as orphan
                if mtime_ok and id_ok:
                    entry.unlink()
                    removed += 1
            except OSError:
                continue
        if removed > 0:
            log.info("pending_slates_swept", removed=removed)
        else:
            log.debug("pending_slates_swept", removed=0)
